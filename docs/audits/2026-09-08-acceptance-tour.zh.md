## 新发现（按严重度）

### 发现 #1（缺陷，建议立项）：api-proxy 偶发 `fetch failed` 导致 UI 错报「发送失败」

- **现象**：巡演首轮（与残留进程资源竞争期间）3 例命中——UI 出现「发送失败 网络请求失败：fetch failed」错误卡，但服务端回合实际已完成，助手回复完整落入 JSONL（retain 现场 `oc-e2e-WTeejU` 复核属实）。干净环境全量两轮（10/10）均未复现。
- **机制**：`desktop/electron/api-proxy.cjs:76` 主进程 fetch 抛出即回 `NETWORK` 错误，UI 直接宣告失败；请求可能已到达服务端并开始执行——用户看到"失败"但回复其实已生成，形成错账。
- **建议方向**：发送路径的 NETWORK 错误在宣告失败前先回查服务端回合状态（GET entries 对照），或引入客户端幂等键让重试安全。

### 发现 #2（缺陷，A-3 FAIL 根因，建议立项）：运行错误行不持久

- **现象**：失败回合的「运行错误」行在后续成功回合完成（或重启、分支重载）后从时间线消失（`A-3/02` 错误行可见 → `A-3/04` 全部消失）。
- **机制**：错误行是 SSE 事件经 `pushStatusEvent` 产生的**仅存活于内存**的 status 条目（`desktop/src/data/projector.ts:554/601`）；任何 `seedItems` 整表重投影（`projector.ts:100`）都会将其冲掉，而 `projectHistory`（`projector.ts:115`）只投影 user/thinking/tool/assistant，不含失败条目。JSONL 侧失败回合无条目可回溯。
- **卡片冲突**：§8 A-3 预期「错误保留，后续消息成功」。现状只满足后半。
- **建议方向**：失败回合写入持久化标记（JSONL 条目或 SQLite 侧表），历史投影渲染为错误行；或产品决策改口为"错误仅当轮可见，历史归日志页"（需回写 §8 预期）。

### 发现 #3（低）：侧栏会话行首轮完成后仍显示「（空会话）」

首轮回合完成后侧栏行预览不更新（`A-1/07`、`A-5/01`），重启或触发会话列表重载后才显示真实预览（`A-4/02`、`B-4/01`）。live 更新缺失，非数据问题。

### 发现 #4（低）：时间线原生条目行对用户是噪音

每次会话初始化产生「条目 session_info / model_change ×3 / thinking_level_change」五行带警告色图标的条目行（如 `A-1/07`）。文案为开发者术语，与"极简、用户可理解"方向有落差；建议友好化（如"已切换模型 xxx"）或默认折叠为一条。

### 发现 #5（低）：错误行正文直接展示原始 JSON

`A-2/01`：`运行错误 401: {"message":"oc-e2e-lane 无效的 API Key（stub 401）"}`。应解析 message 字段以人类文案呈现，原始 payload 收进「在日志中查看」。

### 发现 #6（低）：分支历史弹层分支预览不可区分

`B-3/01`：三条分支的 leaf 预览完全相同（均取助手回复文本）。编辑重生成产生的分支应优先展示改写的用户消息，否则用户无法区分分支。

### 发现 #7（低）：会话标题截断 18 字符

`App.tsx:376` 标题 = 首条消息前 18 字符 + "…"。多条相似开头的会话在侧栏不可区分（巡演中所有会话行标题前缀相同）。可考虑拉长、或后续由模型生成摘要标题。

### 发现 #8（低）：Composer 档位 chip 英文混入

`read-only` / `medium` 等 chip 文案为英文，与全中文界面不一致。
